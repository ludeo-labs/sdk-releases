LudeoResult ludeo_Session_SetLocalization ( LudeoHSession handle,
const LudeoSessionSetLocalizationParams * params )

Changes the Overlay's localization.

The change will only occur if the Overlay actually supports the requested language(s).

Internally, this function is asynchronous (it sends the request to the backend), therefore the return value only tells if the parameters and the SDK state allows the call. It doesn't tell if the actual change was applied or not.

If a change was made, the LocalizationChanged notification is raised. Note that even though it was the client requesting the change, the notification is still raised. The client should take that into consideration and not end up in a loop of calling ludeo_Session_SetLocalization, receiving the notification, and then calling ludeo_Session_SetLocalization again and again.

This design is intentional to allow the developer to test if the client reacts to localization changes request coming from the backend, which would be hard to test otherwise.

A possible way the client can test localization changes at runtime is by (considering en and fr):

  • Start the game in English
  • Once the session is activated, call ludeo_Session_SetLocalization to change to French (fr), BUT don't actually change the game's own language (leave it in English)
  • The backend reacts th the ludeo_Session_SetLocalization call and changes the Overlay to French.
  • The LocalizationChanged notification is received by the game
    • The game looks at the notification details, sees it is a different language from the one it is currently using, and so changes its language to French (to match the Overlay).

In short, the client can use the notification as the point where it changes its own localization, instead of first changing the language then asking the SDK to also change the Overlay.

Parameters
handleThe interface handle.
paramsParameters to the function
Returns
LudeoResult::Success if the call succeeded. By that, it means that all the required parameters were specified, and the information was forwarded to the backend/Overlay. It does NOT mean that localization was actually applied. The reason for this is because internally the operation is actually asynchronous (requires a call to the backend), but since there is nothing the client can do about a possible failure (e.g preferLang not supported by the Overlay), the API is presented as a synchronous operation.
